# 2026-11-17 — 把"完整性"乘成矩阵的测试代价（教训）

## 事实

把 G3 的稳定语料验收设计成 `555 原始文件 × 48 非诊断候选 × 参照/候选两侧`，
共 **53,280 次编辑器进程启动**：

| 维度 | 实际读数 |
| --- | --- |
| 原始语料入口文件 | 555（`stable-31.1` 的 `select_entrypoints`） |
| 非诊断候选 profile | 48（20 配置 × 2 编译器腿，collector 再拆 major/young，扣除诊断产品） |
| 每个 pair 的进程启动 | 555 × 2（参照 + 候选）= 1,110 |
| 严格隔离下每文件耗时 | 约 5–7 s（每文件独立 HOME/TMPDIR + 测试树/产品库/模块夹具铺设 + 9.4MB dump） |
| 单个 profile pair | 约 1.4 h |
| 48 个 profile | 约 27–35 h（`--stable-workers 2`） |
| 上游 `make check` 对照 | 一个构建、同一批文件，约 10–30 min |

## 为什么会变成这样

1. 移植期要求"每个构建变体都要在上游原测上证明与参照等价"，这条要求本身合理；
2. 但把它直接实现为"语料 × 全部变体"的笛卡尔积，没有区分**移植/更新审计**与**日常功能验证**；
3. 严格隔离层（每文件复制测试树、独立产品库/模块夹具）本来是为一致性审计准备的，却被每一条日常验证复用，使单文件成本从上游的 0.1–2.5 s 放大到 5–7 s；
4. 两层放大（矩阵 × 严格夹具）叠加，得到以天计的批次。

## 正确的分界

- **功能一致**：用同一批原始测试样例，对**本次实际要交付/验证的那一个构建**跑一次（参照 + 候选两侧），量级与上游一致。
- **一致性/等价审计**：移植基线、版本更新或结构性改动后，才使用变体矩阵；一次、显式范围、显式时间预算、单列证据。
- 日常开发与优化不得乘变体，不得把审计用的严格夹具成本带进日常回归。

## 破坏性成本（已实测，不是推测）

- 195,460 项的 artifact journal 解锁在 `runtime-owner.py` 的 `artifact_path` 里对每个文件重建并全表扫描 `allowed_roots`（约 4,185 个根）→ 一次解锁 25 分钟以上、CPU 99%。
  修复：`artifact_root_index` 每 journal 只建一次集合，用祖先链查询（与原 `is_relative_to` 语义等价，已核 8 组路径）；同规模解锁降到 **25.5 s**。
- 文件级复用对 donor 的失败/未完成文件（保留态）直接抛错，使整对中断：
  `stable-suite-batch.py` `_try_reuse_file` → `retained donor state is occupied or occupancy is unknown`。
  修复：只放弃该文件的复用、回退 fresh，其余文件继续复用；门禁不降。

## 本轮的停止点（数据保留）

- 已闭合并可核的 profile：**16/48**，每个 555 文件、9,466 case，完成回执与失败计数原样保留。
- 在途被终止的批次 `current-runtime-stable-6-11`（复用被拒后中断）与 `-6-12`（工程控制终止，219/555）保留 partial/controller 记录，artifact owner 均按实际状态释放（`state=released`、`release_failures=[]`），不作为完成证据。
- 48 矩阵不再继续；剩余 profile 不声称完成。

## 规则（写进工程约束）

1. 任何验收先问"这是功能验证还是等价审计"，再决定是否乘变体；
2. 日常验证的预算以官方量级为上限（分钟级），超出先查隔离成本，不许用"完整"当理由铺长时间批次；
3. 变体矩阵必须显式列出 profile 清单、每个 profile 的文件范围、时间预算和停止条件，且只在移植/更新节点执行；
4. 长时间批次不得以"后台在跑"代替对速率的判断：先实测单文件成本并算总账，再决定是否开跑。
