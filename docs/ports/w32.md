## Deviations
- **The `<windows.h>`/SDK section is spelled, not measured.**  C 101, 134-139, 161-163 and 226-263
  name headers with no file in the reference tree (P-88 ①: the declaration site is C's own
  `#include` line, and no file is added under `femacs/src/include/`).  Every scalar is PORTING.md
  1.1's fixed width (`DWORD`/`LONG`/`ULONG`/`UINT` are the 32-bit Windows types whatever this
  target's `c_long` is; `HANDLE` and the SDK's handle records are `void *`), every `#[repr(C)]`
  record is **UNVERIFIED**, and **no `const _` layout assertion is written** for any of them -
  the assertion needs a compiler that has the SDK, and the machine has none (the `w32fns.rs` 10 /
  `w32term.rs` 13 reading of the same situation, where the assertions are owed).
- **`OSVERSIONINFO` and `SYSTEM_INFO` are written here, where `include/w32common.rs` 35-36 and
  `w32fns.rs` 315-319 *defer* them.**  The reason is that this slice embeds both **by value** in
  its own body (C 572's local, C 1174's store) and cannot be transcribed without them; the
  declaration stands at C 101's `#include <windows.h>` line with the SDK's text above it, the
  width is `UNVERIFIED`, and the reconciliation (the mirror's `sysinfo_cache`/`osinfo_cache` then
  resolve, and PORTING.md should have an entry for "an unmeasured SDK record written from its
  citation" - §11) is owed 9.
- **C's `#undef` blocks are carried as C's own text in a comment** (C 51-75 and 227-245).  Their
  target is `nt/inc/ms-w32.h`'s object-like renames, which the mirror spells as `macro_rules!` bound
  at call sites; Rust has no rename to cancel.
- **C's implicit conversions are written out** (PORTING.md 0.3): C 602/C 604's `DWORD`→`LONG`
  (`as LONG`), C 791's `FALSE`→`DWORD`, C 927/C 943/C 964's `ENOTSUP`→`DWORD` (the function returns
  `DWORD`), C 1174's `-1`→`DWORD` (`(-1 as c_int) as DWORD`), C 607's `LONGLONG`→`ULONGLONG`.
- **C's function-pointer cast is a `transmute`**: `(OpenProcessToken_Proc) get_proc_addr (…)` and
  its forty siblings - Rust has no `as` cast to an `Option<fn>` type, and the two pointer widths are
  equal (the `decompress.rs` 237 `LOAD_DLL_FN!` reading).  C's pointer truth tests are the port's
  `.is_some ()`/`.is_none ()` and C's call-through is `.unwrap () (…)`.
- **Three dropped declaration blocks create exactly one unresolved name.**  C 77-89 and C 287-298
  (declarations of functions defined later in the file or in `w32proc.c`) have no Rust item

  its definition is C 7374, so this slice's text alone cannot resolve it - the arm reading's one
  unit-anchored error, stubbed in the pre-flight.
