Core Architecture & Runtime Modernization 核心架构与运行时演进

Fe aims to preserve tagged-object representation and observable Lisp semantics while structuring the build pipeline, evaluator, bytecode interpreter, native-compilation boundary, and garbage collector in auditable Rust modules.

Fe 以保持标记对象布局与 Lisp 可观察语义为约束，将自举构建管线、求值器、字节码解释器、原生编译边界与垃圾回收器组织为可独立验证的 Rust 模块。

Stage 1: Resource Materialization Python + gawk

tools/bootstrap-resources.py reads committed inputs under admin/charsets/, admin/unidata/, src/, and lisp/ along with build-support/generator-recipes.json.

The charset family has 136 distinct outputs in the current recipe set. Other families produce Lisp property tables, generated headers and bootstrap autoloads without touching any external reference directory.

Stage 2: Rust Core & temacs Cargo + xtask

cargo run -p xtask -- build-terminal (or build-macos) compiles the root Rust crate (src/) and links the raw undumped binary temacs.

For the macOS GUI target, xtask also compiles the Swift Cocoa sources in platform/macos/ and links against Cocoa, QuartzCore, and UniformTypeIdentifiers.

Stage 3: pdumper Snapshot emacs.pdmp

temacs --batch -l loadup --temacs=pdump loads the standard Lisp world and serializes the heap into emacs.pdmp (and bootstrap-emacs.pdmp).

The resulting emacs binary (or Femacs.app) maps emacs.pdmp at startup to restore the preloaded Lisp environment.

Bytecode VM (src/bytecode.rs) G5 / G6 · Active

exec_byte_code executes compiled .elc bytecode objects using an explicit stack-frame chain anchored in thread-local GC roots (bc.fp).

  • Active stack values must remain visible through calls, quits and collection; the runtime plan records the exact root and unwind contracts.
  • Dispatch candidates require source-bound semantics and real workload comparisons. Rejected candidates and their evidence are retained; a small benchmark is not full compatibility proof.

Native Compilation Boundary (src/comp.rs) G6 · Active

src/comp.rs manages native .eln compilation units, ABI hash verification, helper link tables, and symbol/immediate relocations.

  • Before registering any native subr, the runtime validates the ABI version, helper table layout, and relocation bounds.
  • Availability depends on the build configuration, compiler library and artifact ABI. Original native bootstrap comparison failures remain open; missing support is not silently counted as compatible.

Read docs/modernization.md →
Interactive Editor Constraint vs. Server Fleets: Every garbage collector balances three coupled axes: throughput (total CPU spent in allocation + barriers + collection), pause latency (tail stop-the-world interruptions on the UI thread), and memory footprint (live heap + metadata + headroom before next collection). Horizontal scaling can increase capacity for partitionable server workloads; it does not eliminate an in-process pause. Here, an interactive editor runs as a single local process where typing, scrolling, IME preedit, and subprocess filters share the main thread with batch Lisp compilation and indexing.
交互式编辑器与服务端集群的本质差异： 任何垃圾回收器都必须在吞吐量（分配、写屏障与回收总 CPU 开销）、停顿延迟（主线程最大停顿时间）和内存占用（存活堆、元数据与触发阈值空间）三者间权衡。横向扩展能增加可分割服务的容量，但不能消除单次进程内停顿。本地交互式编辑器通常是单实例进程：按键上屏、滚屏渲染、输入法预编辑与子进程输出都直面主线程停顿。

Lessons from Go & Java Collectors Cross-Runtime

Go GC & Green Tea (Go 1.25 exp / 1.26 default): Go exposes a unified concurrent collector tuned via GOGC and GOMEMLIMIT (a soft target, not a hard OS RSS cap), while Green Tea reduces mark/scan cost via page-level spatial locality rather than multiplying collector modes.

Java 26 (Serial, Parallel, G1, ZGC): Different collectors prioritize throughput, pause goals and memory differently. A pause target is not a latency guarantee. See the linked modernization plan for primary sources and the limits of applying those lessons here.

Fe Collector Phases & Safety G7 · Active

src/alloc.rs and src/runtime_gc_collector.rs coordinate root discovery (C stack conservative scan, specpdl, bytecode frames, staticpros, pdumper roots), marking, and sweep reclamation.

When foreign OS threads or dynamic module loads (dynlib_open) introduce unverified root producers, the collector permanently falls back to conservative Full collection for safety.

P-437 Fallback Registry Elision Verified Mechanism

Once a process enters permanent Full fallback (foreign thread or dynamic module load), young-cycle candidate registries have no future consumer.

P-437 latches registry capture only when young mode is enabled and permanent fallback is absent. Sweep/commit/abort close the latch; the next Full cycle clears the unusable registry. Paired real-process checks removed roughly 94k entries per later Full cycle while preserving the observed Lisp graph. Elapsed-time improvement is not yet qualified.
