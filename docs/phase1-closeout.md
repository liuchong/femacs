## 1. 目标、设计与范围演变

原目标是对固定参照 `fd7afced403` 的 C/H 运行时进行 Rust 转写，保持文件/符号/布局、算法、
求值顺序、错误与 GC 行为，保留原样 Lisp/文档/数据，并争取性能不低于参照。
原生平台代码使用 Swift/Kotlin 等目标语言，构建使用 Cargo workspace 与 Rust `xtask`，验证使用 Python。
后期优先 macOS 真机和 Android 模拟器，其他平台暂挂；性能尝试失败后用户允许功能性结案。
用户随后要求 macOS 图形版试用，但本轮实际只完成 GUI 构建诊断，该请求未交付，现明确作为遗留结案。

核心并非接入一个现成 VM 库：它是沿用参照语义的 Elisp 栈机，关联 `bytecode.rs`、`eval.rs`、
`alloc.rs`、对象/tag 定义及 dump。栈与常量向量、tagged word、GC 根扫描、gap buffer、区间树与专用哈希表
具有兼容性依据，但“结构成熟”不等于每个操作最优或每行正确。未完成全面同条件替代 VM 横评，不能宣称全局最佳。

```text
输入/文件 → reader/eval/bytecode → 对象、绑定与GC → 编辑缓冲区 → 终端/平台显示
                           ↓
                    dump/pdumper与原样Lisp
macOS Cocoa：Swift单元可编译 → [配置/ABI/联编缺口] → 尚无可运行.app
```

## 4. 性能路线：解决了什么、失败在哪里

1. **PGO**：实现 generate/train/merge/use、训练与评测隔离、工具独立 O2、重签/指纹/dump/配对。
   历史七轮测量较 O2 有收益，但相对参照仍有差距，PGO 仅保留候选，默认仍为 O2 + switch。
   O3 和 native 的具体候选无可靠净收益，未保留为默认。
2. **threaded/asm**：从 toy 讨论到真实 VM 热叶；旧六项 A/B 均更慢。toy 不能证明整个 VM 路线的上限；
   状态交接/慢路成本是解释，未做完因果隔离，不能把所有差距都归因派发。
3. **协调方实际复核**：归档 helper 的 18 个整数 tag 检查接受 0，但 fixnum 低两位是 2。
   隔离修正 tag、后向跳转回原 safepoint、先恢复 LR 再释放栈后，启动仍误判合法 `C-h` 并退出 255。
   因功能已失败，没有对修正模式做性能达标判定，未接入默认；到此停止深究。
4. **独立三轮中位数**：默认 bytecode 为参照 1.35–1.59 倍；load 为 2.36 倍。
   历史 PGO load 的 2.0439 倍是另一构建/采样，不混写成默认本轮读数。

## 5. GUI 调查：已纳入收尾的实际缺口

8 个 Swift 单元均单独编译成功，但源码可编译并不是产品可以联编/启动。
现有配置是关闭 NS 的 Darwin 终端配置；最小 NS 开关诊断的 `frame.c` 两个 pass 各有八处 geometry 作用域错误，
且还涉及 `no_value` 关联。这个诊断不是完整 Cocoa 配置，不能把该错误数当最终 GUI 缺陷总数。
Swift 显式导入 1437 个名字，与当前终端对象加 Swift 对象核对有 1000 个未提供，其中包括 SDK/未启用分支；
544 个同时在旧清单中被记为 core-export 欠账。它们也不是最终链接错误总数。
还有编译器警告，如 raw pointer 到 NSView 的转换 always fails，不能忽略退出 0 与行为正确的区别。

**真实 GUI 仍需完整 Cocoa 配置及布局/全局表、Rust 图形分支、Swift/Rust ABI 提供者、完整链接、dump与应用打包，
最后验证窗口、编辑保存、菜单、输入法、剪贴板和退出。** 本期没有产出 GUI 程序，也没有用终端套壳替代。

## 6. 困难、经验与协作失误

- 工具链/PATH 漂移会改变 `clang` 条件门、archive 与 llvm profile；已采用可核验工具来源、隔离根和配对指纹。
- 发生过 API 额度/端点错误、机器重启、资源中断和构建缓存丢失；恢复、等待、返工必须与正常施工时间区分。
- 覆盖清单、单元编译、完整链接、真实运行、逐用例兼容性是不同证据；旧“7/8”不能掩盖 GUI 未交付。
- 双方应基于代码和实验相互质疑；意见一致不是实验成功，方案失败不等于所有可能方案都失败。
- 协调方此前只有小功能探针时，没有独立复现性能；后来才补做完整构建和三轮对照，不能把旧判断追认为已验证。
- 守护曾未及时恢复已停止的 goal、问题只发 Slack 而未在本聊天说清，用户指出后已纠正；守护现已停用。
- 第一次自动 PTY 未完成设备查询握手，造成等待并被回收；后以系统 `script` PTY 回复查询后完成真实编辑闭环。
- **目标生命周期误操作**：用户原意是保留目标并标 done，协调方却引导为 clear；实施者亲自执行了 `/goal clear`。
  这清除了目标记录，不能说原生 goal 已标 done。用户事后纠正后不再重建、不补造状态；保存原 ID、统计和事实。
  随后原 CLI 最终回报遇到上游 503，同会话重试亦失败；已写总结与已发生的清除不因回报失败而撤销。
