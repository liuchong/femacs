# Phase 1: one-to-one port plan

[femacs](../README.md) replicates GNU Emacs: the C sources are ported to Rust
one file at a time and one statement at a time, and the Emacs Lisp sources are
copied unchanged.

- **Baseline**: the `emacs/` checkout at `fd7afced403` (GNU Emacs 32.0.50). It is
  git-ignored and is the only reference for every port.
- **Companion**: [port-map.md](port-map.md) is the generated file-by-file
  correspondence — names, line counts and status. It is data, not prose.
- **Phase 1 goal**: every C source of the reference tree exists as a Rust source
  with the same name, the same structure and the same semantics, and the shipped
  Emacs Lisp tree runs on the result.

## 2. Fidelity rules

**R1 — Names.** Every ported file keeps its name: `src/NAME.c` becomes
`femacs/src/NAME.rs`; `src/NAME.h` becomes `femacs/src/include/NAME.rs`; other C
directories keep their own directory name under `femacs/`. No renaming, no
merging, no splitting.

**R2 — Identifiers.** Functions, macros, enums, structs, union members and
globals keep their exact spelling: `Ffuncall`, `Lisp_Object`, `CHECK_STRING`,
`Vload_path`, `Qnil`, `struct Lisp_String`, `GC_MARK_STACK`. A C `#define` that
carries code becomes a `macro_rules!` of the same name; a C `#define` that
carries a constant becomes a Rust constant of the same name.

**R3 — Translation units and ABI.** One `.c` file becomes one independently
compiled Rust file, exactly as C translation units are compiled independently.
Each Rust file declares what it uses, and `src/NAME.h` is textually included the
way C includes it — Rust `include!("include/NAME.rs")` mirrors `#include
"NAME.h"`. Exported symbols use `#[no_mangle] pub unsafe extern "C" fn` with the
C name, so C and Rust objects link into the same binary and the tree can be
switched over one file at a time.

**R4 — Layout.** `#[repr(C)]` structs with the same member order; tag bits, GC
bits, `USE_LSB_TAG`, and every size/offset are identical to C. Both sides assert
it at compile time: C `offsetof`/`verify` against Rust `offset_of!` and
`const` assertions. A layout that cannot be expressed this way is a recorded
deviation, not a redesign.

**R5 — Semantics.** Control flow, error model and memory behaviour are
preserved: `sys_setjmp`/`sys_longjmp` plus `record_unwind_protect` for errors
(no Rust `Result`, no `Option`-based control flow, no panic across FFI), the
mark-sweep collector with conservative stack scanning, the same allocator. Rust's
global allocator is never installed.

**R6 — Statement parity.** Definition order inside a file follows the C file, and
one C statement becomes one Rust statement. Line counts are expected to stay
close, but where Rust has a different construct — a `match` for a `switch`, a
closure for a function pointer plus context — the deviation is recorded per file
in the port map rather than forced into fake parity.

**R7 — Generated sources are generated, not ported.** `src/config.h`,
`src/lisp.mk`, `src/emacs-module.h`, `lisp/loaddefs.el`, `etc/DOC`, the
`admin/unidata` and `admin/charsets` tables stay generated by the reference
build procedure. Byte-identical output is a verification target, not a port
target.

**R8 — Verbatim trees are copied, never edited.** `lisp/`, `test/`, `etc/`,
`doc/`, `leim/`, `admin/`, `m4/`, `build-aux/`, `nextstep/`, `java/`, `msdos/`,
`cross/`, `modules/`, the root build files and the ChangeLogs are copied with
their paths preserved. No file in those trees is modified, reformatted or
translated.

## 4. The loading ladder

Progress is measured by how much of the shipped Lisp tree runs:

| Rung | Loads | Status |
| --- | --- | --- |
| L0 | hand-written expressions | target of 1A |
| L1 | all of `lisp/emacs-lisp/*.elc` | target of 1B |
| L2 | `subr.elc`, `simple.elc`, `loaddefs.elc` | target of 1C |
| L3 | the complete `loadup.el` preloaded set | target of 1D |
| L4 | `make -C test check` default selector | target of 1E |
| L5 | the whole test suite including `:expensive-test` | phase 1 exit |

## 5. Verification

1. **ERT against either binary.** `test/Makefile.in` takes `EMACS` from the
   command line, so `make -C test EMACS=…/femacs check` runs the upstream suite
   against the port. The suite is the acceptance criterion, not a proxy for it.
2. **Differential runs.** The same Lisp expressions are evaluated by the
   reference and by the port in `--batch`, and stdout, stderr and exit status
   must match byte for byte.
3. **Layout assertions.** Generated C/Rust assertions cover every shared struct;
   a mismatch fails the build.
4. **Binary interchange.** `.elc` files (bytecode and coding cookie), dump files
   and dynamic modules must load in both directions.
5. **Generated artifacts.** `admin/unidata`, `admin/charsets`, `src/lisp.mk` and
   `ldefs-boot.el` produced by the port must be byte-identical to the reference
   output.
6. **Performance.** Measured after functional parity: startup, editing latency
   and bulk operations against the reference build.

## 6. Build integration

The reference build system stays in charge: it already knows about `loadup`,
`DOC`, `leim`, the unidata tables and dumping. A per-file switch decides whether
`src/NAME.c` or `femacs/src/NAME.rs` is compiled into `temacs`, so the tree can
be migrated one file at a time and either version can be built at will. Rust
files are compiled as independent units (`--emit=obj`, `-C panic=abort`, one
codegen unit) and linked with the still-C files into a single binary with a
single symbol space. The switch table is generated from the port map.

## 7. Unsafe policy

`unsafe` is expected and allowed, because the point is to reproduce C semantics.
It is scoped, not casual:

- Points that are inherently unsafe — tagged pointers, object layout, the
  collector, `setjmp`/`longjmp`, raw buffers, FFI — may use `unsafe` freely.
- Every `unsafe` block carries a `SAFETY:` comment naming the C invariant it
  reproduces.
- No panic may cross an FFI boundary (`panic = abort`, no `Result` plumbing).
- Unsafe is never used to invent behaviour the C source does not have.

## 8. Per-file workflow

1. Port: translate the C file into `femacs/src/NAME.rs` following R1–R6.
2. Assert: add or extend the layout assertions for its structs.
3. Build both ways: compile with the switch on and off; both must link.
4. Test: differential run plus the affected ERT groups.
5. Record: `python3 tools/gen-port-map.py` updates the status and line counts in
   `docs/port-map.md`.
6. Commit: signed commit with `port(NAME): …`, pushed.

## 9. Known deviations (seed of the ledger)

| Deviation | Reason | Handling |
| --- | --- | --- |
| `bytecode.c` uses computed `goto` | Rust has no computed `goto` | `match` or inline assembly; recorded in the port map, measured against the reference |
| `src/*.m` (Objective-C) | not C | Rust plus `objc_msgSend` FFI or an Objective-C shim; batch 1F |
| `src/haiku_*.cc` (C++) | not C | batch 1F |
| `gnulib` (`lib/`) | third-party portability shims | ported 1:1 in batch 1G |
| `comp.c` needs `libgccjit` | external library | FFI to `libgccjit`, ported 1:1 in batch 1E |

## 10. Open decisions

1. Whether the Objective-C backends are ported to Rust or kept as a thin
   Objective-C shell.
2. Whether gnulib stays C behind FFI or is ported in phase 1 (currently batch
   1G).
3. Which platform backends ship in phase 1 (`x*`, `pgtk*`, `w32*`, `haiku*`,
   `android*`, `msdos*` are all inside the scope above).
