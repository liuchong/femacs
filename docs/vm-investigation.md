## 来源与设计判断

- Rust 核心主要转写固定参照 `fd7afced403`；Lisp/测试/数据直接复制。
  新写 Rust 不等于重新发明算法。构建、验收工具及 asm 候选属于项目新增实现。
- VM 是本项目实现的 Elisp 栈机，不是接入通用 VM 库；`bytecode.rs`、
  `eval.rs`、`alloc.rs` 和 `include/lisp.rs` 共同承担执行/绑定/对象/GC。
  xtask 的 Cargo 依赖表为空不等于整个产品无系统库依赖。
- 栈与常量向量、tagged word、混合根扫描、gap buffer、增广红黑区间树及
  专用弱哈希表，均有保持既有字节码、对象、dump 和编辑行为的依据。
  这支持“本期约束下合理”，不证明逐行正确、内存安全或负载上的全局最优。
- 区间树源码明确记录部分 previous/next-overlay-change 操作仍有 O(N) 情形。
  不因结构名字成熟，就把其所有操作概括为对数复杂度。
- 有移植方法调研、ABI/Miri/ASan 探针和性能实验；未找到全面同条件 VM 候选横评。
  当前项目没有代码图索引，本次关键判断来自直接源码和原始记录，不冒充完整代码审计。
- 相关替代品的一手资料：[Remacs](https://github.com/remacs/remacs) 自述不再维护；
  [Rune](https://github.com/CeleritasCelery/rune) 自述早期实验/MVP，其 Lisp 基于 29.1；
  [Cranelift](https://cranelift.dev/) 是代码生成后端，不提供完整的本语言运行时。
  本次只查阅这些公开说明，没有据此重做三者的源码审计或完整性能横评，也不直接切换 VM。

## 派发方案的实际结论

先前两指令 toy 失败，不能推导完整 VM 的性能上限或所有 asm 方案不可行。
双方读过实际 frame、GC、handler、共享尾、tag 和派发体后，才讨论出 asm 热叶：
简单指令连续执行，复杂/慢路径返回仍存活的原 Rust exec 帧，避免搬走 setjmp。
可实现不等于有收益；最终真实 VM 六项 off/on 均更慢（见 P-325 及
[派发计划](bytecode-threaded-plan.md)）。

这是本轮具体实现的否证，**不是所有 threaded/asm 技术的普遍否证**。
“状态交接/慢路重入抵消收益”目前是实现者的解释，未独立采样隔离各项成本。
也没有证据把所有剩余差距都归因于派发：既有 PGO 样本中 load 仍为参照 2.0439 倍。
本轮不重复该性能实验，不继续改寄存器分配、JIT、算法或全 asm。

  这不是完整恶意字节码验证器，不覆盖操作数缺失、无效跳转或常量越界。

## 本轮完整核验设计与执行顺序

先写齐本报告和探针，再集中运行一次，不进行局部反复试错。

| ID | 对象/层次 | 输入与预期 |
| --- | --- | --- |
| V1 | 完整程序的小范围集成输入 | 编译后的加法返回 42；两侧各一次 |
| V2 | 同上，错误路径 | 编译后的主动 error 返回 error 类别；两侧各一次 |
| V3 | 同上，保留 opcode | opcode 0 被捕获为 Invalid byte opcode；两侧各一次 |
| V4 | 同上，修复覆盖的默认臂 | 从真实 DEFINE 列表选一个未定义低位 opcode，返回同一错误；两侧各一次 |
| S1 | 分类分支隔离夹具 | 两侧 10 次、零失败，分类 same |
| S2 | 同上，判别力反例 | A/B 失败身份交换、总失败数都为 1，现分支仍分类 both-fail |
| S3 | 同上，判别力反例 | 10 次与 9 次、都零失败，现分支仍分类 same |
| S4 | 同上，覆盖反例 | 两侧零次，现分支分类 same；不算功能通过 |

探针直接提取当前 `check-ert.py` 的 AST 分类分支，不复制另一套分类规则；
四个夹具证明工具的具体信息缺失，不表示真实套件一定隐藏同样的缺陷。
每个用例分别记录单调时钟耗时，程序/dump 保存 SHA-256，最多每次子进程 10 秒。
生产程序运行经当前 controlled-run 的 runtime 保护；不编译、不安装新依赖。

执行命令（仓库根）：

```sh
python3 ~/.assistant/skills/controlled-run/scripts/run.py --profile runtime -- python3 spikes/vm-closeout/check.py
```

### 最终读数

V1–V4 两侧共 **8/8 符合预期**，子进程均 exit 0。V4 从真实定义列表选出的未定义低位 opcode 为 **51**；0 和 51 两侧均捕获为 Invalid byte opcode。

S1–S4 的四个夹具均重现表中分类：失败身份不同仍 both-fail，运行数不同仍 same，零次仍 same。这是统计工具限制的反例成立，不是对其全面正确的验收。

单次集中探针约 **0.36 s**，执行器记录峰值约 **16.1 MiB**，正常退出且完成回收；短进程可能落在采样间隔之间，该峰值不当作整个 VM 的内存保证。机器结果保留每例耗时与程序/dump 哈希；未运行新的性能对比。
